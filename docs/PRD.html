01

Problem

Developers who run several AI coding agents at once lose track of what each agent is doing and why. The work is spread across separate terminals, branches and pull-request tabs, with no shared record of the plan or the decisions behind each change. They end up babysitting sessions, relaying CI errors by hand, and reverse-engineering intent from diffs, so they hesitate to merge agent work they can't follow.

1aOpportunity

If parallel agent work becomes legible, developers can delegate whole features instead of single prompts and merge the results with confidence. That moves AI coding from "watch it type" to "review what it decided". The MVP is for individual developers who already run two or more agents at once; the survey figures above come from individual developers and support that focus. Teams are a later opportunity, not the evidence for this build.

1bUsers & Needs

Primary users

Developers (indie builders, startup engineers, students on project teams) who already use Claude Code or Codex and run two or more agent sessions at a time. They want to ship more without losing control of their codebase.

Secondary users

Teammates who review agent-made pull requests, and instructors, classmates or hiring reviewers who watch a recorded run to understand how the agents worked.

As a developer running several agents, I need to see in one place which agent is waiting on me because blocked agents sit unnoticed in background terminals.

As a developer, I need to see the orchestrator's plan before and during execution because I can't trust work I can't follow.

As a developer reviewing an agent's pull request, I need to know why each change was made because reverse-engineering intent from a diff is the slowest part of review.

As a developer, I need CI failures sent back to the agent that caused them because copying error logs between windows is pure babysitting.

As a reviewer or classmate, I need to replay a run without installing anything because setting up agent CLIs and logins is a barrier just to look.

02

Proposed Solution

Helix is a web app that runs on your computer and coordinates Claude Code and Codex agents working in parallel on your repository. You describe the outcome you want; an orchestrator agent breaks it into tasks and shows you the plan as a graph. Nothing starts until you approve it. Each task then gets its own agent and git branch, and Helix carries it through pull request and CI to a merge-ready state. You decide when to merge; in the MVP every merge is a human click. Every step is recorded with its cause, so Helix can replay the project's history to any moment and explain why each change happened, saying whether each explanation came from the plan, from Helix's own record, or from the agent's summary of itself. You can delegate bigger work and merge it with confidence instead of babysitting terminals.

Agents in this build

  • Workers: Claude Code and Codex sessions, one per task, each on its own branch. Built, and verified with real Codex and Claude Code runs.
  • Orchestrator: one Claude Code planner session per goal that submits the structured plan, including the files each task expects to touch and which agent does each task. Built. Its plan waits for your approval before any worker starts.
  • Reviewer: built, and always the other agent. When a worker’s pull request passes CI, Claude Code reviews Codex work and Codex reviews Claude Code work; no agent reviews its own. The reviewer can read the pull request but never edit it. Requested changes go back to the worker as feedback, and the pull request is ready to merge only after the review approves its latest version.
  • Helix itself is not an agent. It is the coordinator that validates plans, routes feedback and commits each turn. It never merges on its own.

WHY

Example run, illustrative. Drag the timeline to replay the board and read the Why line for each event. Each Why line says where it came from: stated in the plan, recorded by Helix, or the agent's own summary. Replay changes what you see, not your repository. This is the core Helix interaction.

2aValue Proposition

Developers who juggle multiple AI coding agents and lose track of what each one is doing use Helix, a local web app for orchestrating Claude Code and Codex, to delegate a feature and follow it from an approved plan to a merge-ready pull request. Unlike terminal multiplexers and existing orchestrators that show status but not reasoning, Helix records every event with its cause so you can approve the plan, replay any moment, and ask why. Developers review agent work faster and trust what they merge.

2cGoals & Non-Goals

Goals

  • Developers can delegate a multi-part feature and get merge-ready pull requests, approving the plan up front and each merge at the end, and otherwise stepping in only when asked.
  • Developers can explain any agent change (what changed, why, and what triggered it) without reading the full transcript.
  • Anyone can experience Helix from a link, with nothing installed.
  • The full loop runs reliably enough to demo live on a real repository.

Non-Goals

  • Agents beyond Claude Code and Codex. The adapter interface is ready; other agents are deferred.
  • Desktop, mobile or cloud versions. A local web app keeps setup and demos simple.
  • Cost and token tracking. Provider numbers are inconsistent, and Agent Orchestrator removed theirs for overstating spend. Runaway spend is limited by turn caps, a parallel-worker limit and a stop-all control instead.
  • Autonomous merging. Helix brings work to a merge-ready pull request; every merge needs a human click in the MVP.
  • Restoring the past. The timeline replays history in the interface. It does not roll back files, branches or agent sessions.
  • Scheduled automations and team accounts. Single-user, on-demand work only for the MVP.
  • Agent bake-off (same task run by both agents and compared). Stretch goal after the demo.

03

Requirements

P0 is the demo loop and nothing else: add a project, approve a plan, start and watch tasks, answer an approval, see the diff, have a CI failure routed back and fixed, merge with a click, and explain it all through the plan graph, timeline replay and Why panel. Building has been fast; proving that these behaviors hold up together is the slow part, so everything outside the loop sits at P1 or below.

Technical approach

Browser (React) ──HTTP/SSE──▶ helixd (Node daemon, localhost only) ──▶ SQLite event log
      │    └──WebSocket──▶ terminal host (node-pty / ConPTY)   ├─▶ Claude Code + Codex adapters
      │                                                         ├─▶ git worktree manager
 same app, static ◀── recorded .helixlog (demo mode)            ├─▶ GitHub PR / CI observer
                                                                └─▶ helix CLI ◀── orchestrator agent

Every action is an append-only event, and each event can point to the event that caused it. The screen is computed from events up to a moment in time, so the live view, timeline replay, demo replay and the future bake-off comparison all use one mechanism. Status labels are always derived, never stored. Codex agents build the daemon and integrations in parallel work packages; Claude owns the interface and reviews every package before merge.

Keeping parallel work mergeable

Separate branches don't solve integration on their own. For the MVP, Helix follows one narrow policy:

  • Each task in a plan declares the files it expects to touch. Helix rejects a plan where two parallel tasks claim the same file; the orchestrator must serialize them or make one task the owner.
  • When parallel tasks share a new interface, the orchestrator first plans a contract task that defines it. That task merges before either dependent starts.
  • A dependent task starts only after its prerequisites merge, from a freshly fetched origin/main, so the upstream code is already in its workspace.
  • After every merge, Helix re-checks the other open pull requests and sends any that now conflict back to their worker as a merge-conflict fix.

Helix can check that a plan is well-formed and that file claims don't overlap. Whether the plan really cuts the work cleanly is a question of model quality that no validator answers.
