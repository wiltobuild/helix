1. **Blocker — Every fresh chat session sends its initial prompt twice.**  
   [core.ts:397](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/core/src/core.ts:397), [claude.ts:85](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/harness/src/claude.ts:85), [codex.ts:96](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/harness/src/codex.ts:96)

   Both real adapters send `session.prompt` inside `start()`. After `start()` returns, core sends the same prompt again. A normal session therefore executes the task twice, potentially making additional edits after its first turn has already triggered shipping. Core also has no separate turn cause recorded for this second execution.

   **Fix:** Give core sole ownership of initial delivery; adapter startup should establish the session without starting a turn.

   **Verified:** Ran real adapter startup methods with transport mocked in memory, composed with real core and in-memory SQLite. Both adapters received `['first', 'first']`. Core’s test harness does not perform automatic initial delivery, so its golden test hides this mismatch.

2. **Blocker — Dependent workers start from a base that does not contain their merged dependencies.**  
   [core.ts:628](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/core/src/core.ts:628), [core.ts:648](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/core/src/core.ts:648), [manager.ts:120](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/git/src/manager.ts:120)

   Scheduling checks that prerequisite PRs are merged, then creates the dependent worktree from `p.defaultBranch`. Git resolves that local ref without fetching. SCM merging changes GitHub, not local `main`.

   **Failure scenario:** Worker A adds an API and merges remotely. Worker B depends on A, starts immediately, and receives the old checkout without that API. Even fetching `origin/main` separately would not update the local `main` used here.

   **Fix:** Explicitly fetch and resolve a remote base containing the prerequisite merges before scheduling dependents. Create from that verified ref/SHA without resetting the user’s local branch.

   **Verified:** Traced merge → scheduling → worktree creation end to end. No intervening fetch or base update exists. The golden test checks that the dependent starts, using a fake Git service; it never checks its checkout contents.

3. **Should fix — Interrupting a turn corrupts causal links, especially with queued messages.**  
   [core.ts:296](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/core/src/core.ts:296), [core.ts:442](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/core/src/core.ts:442)

   `deliver()` replaces `runtime.cause` before awaiting interruption. The cancelled turn’s final emissions consequently inherit the replacement message’s cause. If another message was already queued, the replacement turn’s subsequent `active` event consumes that older queued cause.

   **Failure scenario:** A runs, B is queued, then C interrupts. A’s cancellation output points to C; C’s execution points to B. Subsequent causes remain displaced.

   **Fix:** Preserve A’s cause until its terminal boundary, insert C ahead of B in the pending turn causes, and activate C’s cause only when C starts.

   **Verified:** Reproduced with real core, SQLite, and the real `ProcessSession` queue/interruption implementation using an in-memory transport. Observed cancellation attributed to `replacement` and replacement activity attributed to `queued`.

4. **Should fix — The next harness turn starts before core finishes snapshotting and shipping the previous turn.**  
   [session.ts:248](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/harness/src/session.ts:248), [core.ts:450](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/core/src/core.ts:450)

   `completeTurn()` emits `idle`, then automatically pumps the next queued turn. Core merely enqueues handling of that emission; its `markTurn`, diff and push operations run asynchronously afterward. Core’s command serialization does not serialize the external agent’s filesystem changes.

   **Failure scenario:** Turn B starts editing or committing while core snapshots turn A. A’s snapshot can include B’s partial edits, and a push attributed to A can include B’s commits.

   **Fix:** Keep pending turns in core and dispatch the next only after end-of-turn bookkeeping finishes, or introduce an explicit internal acknowledgement before the harness pumps another turn.

   **Verified:** A probe using the real queue implementation showed `['first', 'second']` already started when the first turn’s `markTurn` callback ran; the callback observed `second`. Existing core fakes require manually emitted activities and do not reproduce this scheduling.

5. **Should fix — External merges lose the `pr.merged` event and merge SHA.**  
   [github.ts:348](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/scm/src/github.ts:348), [core.ts:518](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/core/src/core.ts:518)

   SCM publishes `pr.updated` with `state: 'merged'` before publishing `pr.merged`. Core applies the first event, stops watching, and then rejects the queued `pr.merged` because its current PR is no longer open.

   **Failure scenario:** A human merges through GitHub. The board shows merged and dependents start, but the durable log lacks the merge event and its `mergeSha`; dependent causality points to `pr.updated`.

   **Fix:** Accept and deduplicate `pr.merged` even after a merged-state update, or publish the authoritative merge event first.

   **Verified:** Composed real SCM, real core, in-memory SQLite and fake GitHub. An external merge produced `pr.updated` but zero persisted `pr.merged` events.

6. **Should fix — Review repairs stop after a head change when the review summary stays unchanged.**  
   [github.ts:357](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/scm/src/github.ts:357), [core.ts:536](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/core/src/core.ts:536)

   SCM emits `ci.updated` when the head changes, but emits `review.updated` only when the normalized review summary changes. Core routes review feedback exclusively from `review.updated`, despite deduplicating repairs by head SHA.

   **Failure scenario:** Review requests changes on H1. The worker pushes H2, but changes remain requested. SCM emits the new head without a review event, so core never attempts another repair for H2. New review comments that leave the summary unchanged are likewise invisible.

   **Fix:** Re-evaluate outstanding review feedback on head changes, at minimum using the same head-change condition as CI. Preserve the existing per-head deduplication and attempt cap.

   **Verified:** Real SCM/core probe observed one routed repair on H1 and none on H2 with an unchanged `changes_requested` summary.

7. **Should fix — Default terminal launches cannot reliably run Windows CLI installations.**  
   [core.ts:332](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/core/src/core.ts:332), [host.ts:113](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/pty-host/src/host.ts:113)

   Terminal mode passes bare `claude` or `codex` directly to node-pty. It bypasses the executable resolution and batch-shim handling implemented for chat mode. The pinned ConPTY implementation searches literal filenames and ultimately uses `CreateProcessW`; it does not supply the missing PATHEXT/shell handling.

   **Failure scenario:** Codex is available through an npm `codex.cmd` installation. Chat mode resolves and runs it, while creating a terminal session fails.

   **Fix:** Resolve terminal executables explicitly. Prefer a native executable; where a shim is necessary, use a launcher with safe argument transport for prompts containing quotes and shell metacharacters.

   **Verified:** Traced the default terminal path through the pinned node-pty JavaScript and native sources. Native execution was not run. Existing PTY integration tests launch `process.execPath`, so they do not test this path.

8. **Should fix — Stopping immediately after Windows PTY creation can reject and leave the terminal running.**  
   [host.ts:232](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/pty-host/src/host.ts:232), [process-tree.ts:23](C:/Users/Wil/Documents/Projects/helix-wt/w1-review/packages/pty-host/src/process-tree.ts:23)

   `spawn()` resolves before ConPTY’s asynchronous connection assigns its process ID. During that interval, node-pty exposes PID `0`. `kill()` immediately passes it to `killProcessTree`, which rejects; execution never reaches native PTY cleanup.

   **Failure scenario:** A user immediately stops a newly created terminal session, or daemon shutdown overlaps startup. Stop fails with `INVALID_REQUEST`, and the terminal can subsequently finish starting.

   **Fix:** Track startup readiness and cancellation explicitly. A stop during startup must cancel startup or wait for a valid process handle and terminate it, with bounded cleanup.

   **Verified:** Confirmed the asynchronous PID assignment in the pinned dependency. An in-memory PTY probe with initial PID `0` reproduced `INVALID_REQUEST` and a terminal still present in `list()`. Existing fake PTYs start with a valid PID.
